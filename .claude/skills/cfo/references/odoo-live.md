# الربط الحي مع Odoo

`scripts/odoo_fetch.py` يقرأ من Odoo مباشرة عبر JSON-RPC. **قراءة فقط:** السكربت يرفض أي دالة غير `search_read` و`search_count` و`read`، فما يكدر يعدّل أو يحذف شي حتى لو انطلب منه.

## الإعداد (مرة وحدة، يسويه المستخدم)

1. **مستخدم مخصص بـ Odoo** بصلاحيات قراءة فقط. لا تستخدم حساب المدير. الإعداد المقترح:
   - المحاسبة: Accounting / Read-only (أو Auditor حسب النسخة)
   - المشتريات: User (للقراءة)
   - الموافقات: User
2. **مفتاح API** لهذا المستخدم: Preferences ← Account Security ← New API Key.
3. **متغيرات البيئة** بإعدادات البيئة السحابية (قائمة البيئة بشريط عنوان الجلسة ← Edit):
   - `ODOO_URL`: رابط Odoo مثل `https://erp.company.iq`
   - `ODOO_DB`: اسم قاعدة البيانات
   - `ODOO_USER`: اسم دخول المستخدم المخصص
   - `ODOO_API_KEY`: المفتاح (يُحفظ كسر، **لا يُلصق بالمحادثة ولا يُكتب بالمستودع**)
4. **الشبكة:** أضف مضيف Odoo إلى Allowed domains بإعدادات الشبكة للبيئة.
5. ابدأ جلسة جديدة حتى تُقرأ المتغيرات.

**إذا Odoo على شبكة داخلية بدون رابط عام:** البيئة السحابية ما توصل له. البدائل: تشغيل Claude Code على جهاز داخل الشبكة، أو تصدير يدوي من Odoo (CSV/XLSX) يُعطى للسكربتات مباشرة، لأن `validate_costs.py` يفهم عناوين تصدير Odoo (Date, Account, Partner, Label, Debit, Credit).

## الأوامر

| الأمر | يعطي | متى |
|---|---|---|
| `snapshot` | النقد بكل حساب، وأعمار الذمم المدينة والدائنة وأكبر 5، والفواتير غير المسددة والمتأخرة، والمشتريات المفتوحة حسب الحالة والعملة، وطلبات الموافقة المعلقة، والإيرادات والمصاريف للشهر والسنة | بداية أي محادثة مالية تحتاج الصورة الحالية، أو سؤال مثل "شلون وضعنا؟" |
| `costs --from --to --out` | قيود المصاريف المرحّلة بصيغة سجل التكاليف | قبل `build_cost_workbook.py` |
| `trial-balance --from --to --out` | ميزان المراجعة مع فحص التوازن | لمطابقة تقرير التكاليف مع الدفاتر |

**خيارات `costs`:**
- الافتراضي: الحسابات من نوع `expense` و`expense_direct_cost` و`expense_depreciation`.
- `--account-prefix 3`: كل الحسابات اللي رمزها يبدأ بـ 3. يناسب دليل الحسابات المبني على النظام المحاسبي الموحد.
- `--code-digits 4`: يقص رمز الحساب (مثل 320101) إلى 4 أرقام (3201) حتى يطابق `cost_codes.csv`.
- `--include-capex`: يضيف حسابات الأصول الثابتة.

**كيف تتحول البيانات:**
- **المبلغ:** `balance` بعملة الشركة (مدين − دائن)، فسعر الصرف = 1. التحويل حصل بـ Odoo بتاريخ المعاملة.
- **مركز الكلفة:** من `analytic_distribution`. السطر الموزع على أكثر من حساب تحليلي يتقسم إلى أسطر حسب النسب.
- **رقم المرجع:** رقم فاتورة المورد (`ref`) إذا موجود، لأن الفاتورة المكررة تاخذ رقماً داخلياً جديداً بـ Odoo لكن رقم المورد نفسه، فهو أفضل لكشف التكرار.
- **حالة الدفع:** من `payment_state` لفواتير الموردين. `in_payment` تُحسب "مدفوع".

## التوافق

- **Odoo 16 إلى 18:** مدعوم (يعتمد على `account_type` و`analytic_distribution`).
- **Odoo 19 فما فوق:** واجهة JSON-RPC صارت مهملة لصالح JSON-2 API. إذا ظهر خطأ اتصال، هذا هو السبب المحتمل.
- **Odoo 15 وأقدم:** الحقول مختلفة (`user_type_id`، `analytic_account_id`) ويحتاج تعديل.
- **موديل الموافقات** (`approval.request`) من Enterprise. إذا غير مثبت، القسم يُتجاوز بصمت.

## قواعد الاستخدام للمدير المالي

1. **البيانات الحية تُذكر بتاريخها:** "حسب Odoo بتاريخ 2026-10-17 الساعة كذا".
2. **القيود المرحّلة فقط.** المسودات ما تدخل الأرقام. إذا السؤال عن الالتزامات القادمة، استخدم أوامر الشراء المفتوحة من `snapshot`.
3. **طابق قبل ما تعتمد:** مجموع `costs` لفترة لازم يساوي أرصدة نفس الحسابات بـ `trial-balance`.
4. **لا تعدّل Odoo من هنا.** أي تصحيح (قيد، إعادة تصنيف، تغيير مركز كلفة) يُكتب كتوصية يعتمدها المحاسب ويدخلها بنفسه. هذا فصل مهام وليس قيداً تقنياً فقط.
5. **السرية:** أسماء الموظفين والرواتب التفصيلية ما تُعرض إلا للي يحتاجها.
